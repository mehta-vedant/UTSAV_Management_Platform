1 Project Overview

What is UTSAV?

UTSAV is a production-grade, multi-tenant web application built to help organizations manage large-scale cultural events like Ganeshotsav festivals and community clubs. Think of it as a specialized management tool that handles:

  • Money tracking - Who donated how much, what was spent where, approval workflows for expenses
  • Event management - Schedule ceremonies, assign team members, track registrations
  • Volunteer coordination - Create tasks, assign them, track completion
  • Public transparency - Let the public see how funds are used (without logging in)
  • AI-powered insights - Ask questions like "How much have we spent on decoration?" in plain English

The key word is "multi-tenant" - one codebase serves hundreds of different organizations, and each organization's data is completely isolated from others. After 6 phases of refactoring, the codebase is clean, modular, and interview-ready.

2 Key Concepts (Learn Before Interview)

What is an ORM? (Object-Relational Mapper)

Plain English: An ORM lets you write code like prisma.donation.findMany() instead of writing raw SQL like SELECT * FROM "Donation" WHERE "organizationId" = 'abc123'. It maps your code's objects/tables to actual database tables. You define your schema in code, and the ORM generates the SQL for you.

Prisma is the specific ORM used in UTSAV. It has 3 parts:

  1. Prisma Schema (prisma/schema.prisma) - A file where you define all your database tables, their fields, and relationships. This is your "database blueprint."
  2. Prisma Client - Auto-generated TypeScript code from the schema. You use it to talk to the database: prisma.user.findMany(), prisma.donation.create(), etc.
  3. Prisma Migrations - Commands to sync your schema changes to the actual database. Run prisma db push and Prisma alters the real PostgreSQL tables to match your schema.

What are Server Components vs Client Components?

Plain English: In Next.js 14, React components run on the server by default (Server Components). They can directly access databases, read files, and do heavy work WITHOUT sending JavaScript to the browser. Only add "use client" at the top of a file if you need interactivity (clicks, forms, state, animations). This means most of UTSAV's pages send ZERO JavaScript to the browser - they just send finished HTML.

What are Server Actions?

Plain English: Server Actions are functions that run on the server, called directly from client components. Instead of creating a separate API endpoint (like /api/donations), you write a function with "use server" at the top, and the client can call it like a regular function. Next.js handles the HTTP behind the scenes. In V2, all actions use the withAction wrapper for consistent error handling.

What is JWT (JSON Web Token)?

Plain English: JWT is a way to keep users logged in. When you log in, the server creates a small encrypted token (like a digital ID card) and stores it in your browser's cookie. Every time you make a request, the browser sends this token back. The server decrypts it to know who you are WITHOUT looking up the database every time. It's "stateless" - the server doesn't need to remember your session.

What is Multi-Tenancy?

Plain English: Multi-tenancy means one application instance (one codebase, one database) serves multiple organizations ("tenants"). Think of it like Gmail - one Google servers handle millions of different users' emails, but each person's data is isolated. In UTSAV, the same app serves Festival A, Festival B, and Club C, but none can see each other's data.

What is RBAC (Role-Based Access Control)?

Plain English: RBAC means different users get different permissions based on their role. In V2, this is permission-based (e.g., "finance:read", "members:manage") with 12 granular permissions across 5 resource types. An ADMIN has all 17 permissions, a TREASURER has 9, a COMMITTEE_MEMBER has 9, and a VOLUNTEER has only 3.

Why Prisma over Raw SQL or other ORMs?

We chose Prisma because: (1) Type safety - Every query result is fully typed, so your IDE catches errors before runtime. (2) Schema as code - The database schema lives in a single file (schema.prisma), making it easy to review and version control. (3) Migrations - prisma db push syncs schema changes to the DB automatically. (4) $extends - Prisma's client extension API enabled the multi-tenancy pattern (auto-injecting organizationId into queries). (5) Relations - Easy include/select for nested queries without JOINs. (6) Works with plain functions - After refactoring, services are tree-shakeable exports, not static classes.

5 The 6 Refactoring Phases

Why Refactor a Working Application?

The original codebase worked but had architectural debt: static class services created unnecessary coupling, every action had repetitive try/catch blocks, dashboard pages had 15+ lines of duplicated context resolution, and there were TypeScript errors. Six focused phases addressed each concern systematically - making the code more testable, more maintainable, and interview-ready.

Phase 1: Foundation - Unified Types & Authorization

What changed:

  • ActionResult<T> - Created a unified response type in src/lib/action-response.ts. Every server action now returns either { success: true, data: T } or { success: false, error: string, code?: string }.
  • requirePermission() - Replaced the old 3-tier validateAccess() + role-list matching pattern with a single permission-based function in src/lib/access-control.ts. 12 granular permissions across 5 resource types.
  • TenantContext - Established the pattern for consistent org resolution across all pages.
Impact: Created the type-safe foundation that all subsequent refactoring built upon. Client components can now pattern-match on result.success for type-safe error handling.

Phase 2: Services → Plain Functions

What changed:

  • All 15+ service files converted from class XService { static async method() {} } to export async function method() {}.
  • 53 files changed in this phase alone (the largest single refactoring step).
  • All imports updated from DonationService.createDonation() to createDonation().

Before (Class)

// donation.service.ts export class DonationService { static async createDonation( organizationId: string, data: CreateDonationInput ) { try { // business logic... } catch (error) { throw error; } } } // Usage: await DonationService.createDonation(id, data);

After (Plain Function)

// donation.service.ts export async function createDonation( organizationId: string, data: CreateDonationInput ) { // business logic... } // Usage: await createDonation(id, data);
Why: Plain functions are tree-shakeable (unused exports get eliminated by bundlers), have no this binding issues, are easier to mock in tests, and have a simpler mental model. Static classes provide no runtime benefit in TypeScript.

Phase 3: withAction Wrapper - Eliminate Try/Catch

What changed:

  • Created withAction() and withActionNoReturn() in src/lib/action.ts.
  • Every action file now wraps handlers in withAction(() => handler(), { paths: [...] }).
  • Eliminated all try/catch/revalidatePath boilerplate from 11 action files.
  • Reduced action file size by ~40%.
// src/lib/action.ts - The withAction wrapper export async function withActionNoReturn( handler: () => Promise<void>, options: { paths?: RevalidatePath[] } = {} ): Promise<ActionResult<undefined>> { try { await handler(); if (options.paths) { for (const p of options.paths) { revalidatePath(p.path, p.type); } } return actionSuccess(); } catch (error) { return actionFailure(error); } }
Why: Every action before had the same 10-line try/catch pattern. withAction centralizes error handling, ensures every action returns ActionResult<T>, and automatically handles cache revalidation. Single responsibility: actions only define WHAT to do, withAction handles HOW to respond.

Phase 4: resolveOrgContext - Page Boilerplate Eliminated

What changed:

  • Created resolveOrgContext(orgSlug) in src/lib/org-context.ts.
  • Single call replaces org resolution + validateAccess + isAdmin derivation in all 9 dashboard pages.
  • Net change: 39 lines added, 73 removed (net -34 lines) across all pages.

Before (Each Dashboard Page)

// Repeated in 9 pages const org = await getOrganizationBySlug(params.orgSlug); if (!org) return notFound(); const { user, member } = await validateAccess( org.id ); const isAdmin = member.role === OrganizationRole.ADMIN || member.role === OrganizationRole.COMMITTEE_MEMBER; const isFestival = org.type === "FESTIVAL";

After (Single Line)

const { organization, member, isAdmin, isFestival } = await resolveOrgContext(params.orgSlug); // That's it. org resolution, auth check, // membership validation, and role derivation // all in one function call.
Why: Every dashboard page had 8-12 lines of identical boilerplate. resolveOrgContext encapsulates the entire "who am I and what org am I in?" flow in one call. If the org doesn't exist, it throws. If the user isn't a member, it throws. The page only gets to its rendering logic if everything is valid.

Phase 5: Dead Code Cleanup & Zero TS Errors

What changed:

  • 4 files deleted - unused utilities, deprecated re-exports, orphaned test helpers.
  • All validateAccess() usages in service files migrated to requirePermission() where appropriate.
  • Zero TypeScript errors across the entire codebase (verified with npx tsc --noEmit).
  • Fixed all any types, missing return types, and implicit undefined issues.
Impact: A clean TypeScript build means the compiler validates your entire codebase at once. Zero errors = zero type-safety holes. This is critical for interview confidence - you can say "our entire codebase compiles with zero errors."

Phase 6: Tests Passing & Interview-Ready

What changed:

  • 25/25 tests passing across 10 test files (verified with npx vitest run).
  • Tests updated to match new plain function exports (no more mocking class methods).
  • Added tests for the new architectural patterns (withAction, requirePermission, etc.).
  • Interview preparation materials updated (V2 of this document).
The result: A codebase where every architectural decision is intentional, every pattern is consistent, and the code compiles and tests cleanly. This is what "interview-ready" means.

Schema Design Patterns

Soft Deletes (isArchived)
Instead of deleting records, we set isArchived = true. This preserves data for audit trails, allows "unarchive" operations, and prevents accidental data loss. All queries filter by isArchived: false.
Cascading Deletes
onDelete: Cascade means deleting an Organization automatically deletes all its members, donations, expenses, events, etc. The database handles this, not application code.
Composite Unique Constraints
@@unique([userId, organizationId]) ensures a user can't join the same org twice. @@unique([email, organizationId]) prevents duplicate invite acceptance.
Decimal for Money
Decimal(12, 2) stores exact decimal numbers (e.g., 5000.00). Never use floats for money - they have rounding errors like 0.1 + 0.2 = 0.30000000000000004.

Login Flow (Step by Step)

Why JWT over Database Sessions?

Database sessions require a DB lookup on every request to verify the session is valid. JWTs are self-contained - the token itself contains the user info, cryptographically signed. This means: (1) No DB round-trip for session verification (faster). (2) Works with serverless (Vercel functions are stateless). (3) Scales better - no session table bottleneck.

Route Protection (Middleware)

Middleware runs BEFORE the page loads. NextAuth's withAuth middleware checks if a valid JWT cookie exists. If not, it redirects to /login. This protects all /dashboard and /[slug]/dashboard routes.

Two Levels of Protection

Level 1: Middleware (JWT check)
Runs on EVERY request to protected routes. Simply checks: "Is there a valid token?" If no token → redirect to login. This is fast but coarse-grained.
Level 2: requirePermission() (Granular)
Runs inside services. Checks: "Is this user a member? Do they have the right PERMISSION?" Single function call replaces the old 3-tier pattern. Permission-based, not role-list matching.
8 Multi-Tenancy Deep Dive

How Is Data Isolated Between Organizations?

Every table that contains org-specific data (Donation, Expense, Event, etc.) has an organizationId foreign key column. The multi-tenant Prisma extension (getTenantPrisma()) automatically adds this column to every query's WHERE clause, so you never accidentally read another org's data.

Without the extension, every service function would need:

// Tedious and error-prone - developer could forget organizationId await prisma.donation.findMany({ where: { organizationId: "org_abc", isArchived: false } });

With the extension, service code just writes:

// Clean - organizationId is auto-injected by the extension const tenantPrisma = getTenantPrisma(organizationId); await tenantPrisma.donation.findMany({ where: { isArchived: false } });

The $extends + getTenantPrisma Pattern

export const getTenantPrisma = (organizationId: string) => { return prisma.$extends({ query: { $allModels: { async $allOperations({ model, operation, args, query }) { const tenantModels = [ "Donation", "Expense", "OrganizationMember", "BhogItem", "Event", "VolunteerTask", "AuditLog", "EventAssignment", "EventRegistration", ]; if (tenantModels.includes(model)) { const anyArgs = args as any; // RULE 1: READS - auto-add WHERE organizationId = X if (anyArgs.where) { anyArgs.where = { ...anyArgs.where, organizationId }; } // RULE 2: CREATES - auto-inject organizationId if (operation === 'create' && anyArgs.data) { anyArgs.data = { ...anyArgs.data, organizationId }; } // RULE 3: UPDATES - strip organizationId (prevent migration) if ((operation === 'update') && anyArgs.data?.organizationId) { delete anyArgs.data.organizationId; } } return query(args); }, }, }, }); };

Race-Condition-Safe Expense Approval

If two admins click "Approve" on the same expense at the exact same time, we need to prevent double-approval. We use updateMany with a defensive WHERE clause.
const result = await tenantPrisma.expense.updateMany({ where: { id: expenseId, status: 'PENDING', // Only match if STILL pending }, data: { status: 'APPROVED', approvedById: memberId, approvedAt: new Date() }, }); if (result.count === 0) { // No rows matched = expense was already processed by someone else throw new ConflictAppError("This expense was already processed."); }

Why this works: updateMany is atomic at the database level. Only one transaction will see status = 'PENDING' and update it. The second will see status = 'APPROVED' and get count = 0. No locks, no crashes, no inconsistency.

13 Key Design Decisions

Why Plain Functions Over Static Classes?

Static classes in TypeScript provide no runtime benefit over plain functions. They add syntax noise (ClassName.method() vs method()), prevent tree-shaking (bundlers can't eliminate unused static methods), and create unnecessary this binding gotchas. Plain functions are the idiomatic TypeScript pattern. They're simpler, more testable (just mock the import), and bundle-friendly.

Why the withAction Wrapper?

Every action file had the same boilerplate: try/catch, parse errors, revalidate paths, return success/failure. WithAction centralizes this in one place. The action file only defines WHAT to do (the business logic), and withAction handles HOW to respond (error handling, cache invalidation, return type). This reduced action file size by ~40% and ensures every action returns a consistent ActionResult<T>.

Why resolveOrgContext?

Every dashboard page needed to: (1) resolve slug to org, (2) validate the user is a member, (3) derive isAdmin and isFestival flags. This was 8-12 lines of identical code across 9 pages. resolveOrgContext encapsulates this in one function that either returns the full context or throws (triggering 404). Pages went from boilerplate-heavy to focused on their unique rendering logic.

Why Separate Services from Server Actions?

Server Actions are entry points (like controllers). Services contain business logic. This separation means: (1) Services can be tested independently without HTTP/Server Action overhead. (2) Multiple Server Actions can reuse the same service function. (3) RBAC checks live in services via requirePermission(), ensuring they're never bypassed. (4) Business logic is not coupled to Next.js specifics.

Why Server Components by Default?

Most dashboard pages are data-heavy (tables, stats, lists). Server Components send zero JavaScript to the browser - just HTML. This means: (1) Faster page loads - smaller bundle size. (2) Better SEO - content is pre-rendered on the server. (3) Direct DB access - no API layer needed for reads. Client Components are only used for forms, modals, and interactive elements.

Why Prisma $extends for Multi-Tenancy?

Alternatives considered: (1) Manual WHERE clauses - error-prone, developer could forget. (2) Database Row-Level Security - PostgreSQL RLS is powerful but harder to manage, test, and debug. (3) Separate databases per tenant - overkill for this scale. The $extends approach is transparent (you can see what it does), testable, and fail-safe (missing orgId = empty results, not cross-tenant leaks).

Why Soft Deletes Over Hard Deletes?

Hard deletes are permanent and unrecoverable. Soft deletes via isArchived: (1) Preserve data for audit trails. (2) Allow "unarchive" operations. (3) Maintain referential integrity. (4) Enable data recovery from mistakes. (5) Historical records remain intact for reporting.

Why Decimal for Money?

Floating-point numbers (IEEE 754) cannot exactly represent decimal fractions. Example: 0.1 + 0.2 = 0.30000000000000004. For financial calculations, this causes real bugs. Decimal(12, 2) stores exact base-10 numbers with 2 decimal places, ensuring 0.1 + 0.2 = 0.30 always.

Why Extract the Task Module?

Task logic was originally part of member.service.ts, creating a god-file that handled both member management and volunteer task operations. Extracting to modules/tasks/task.service.ts follows the Single Responsibility Principle. Each service file now handles one domain: member.service handles membership, task.service handles tasks. This makes both files smaller, easier to understand, and independently testable.
14 Interview Questions & Answers

Q1: "Walk me through the architecture"

A: UTSAV is a modular monolith with 5 layers: (1) Presentation - React Server Components + Client Components; (2) Action - Server Actions wrapped in withAction(); (3) Service - Plain functions organized by domain (finance, events, tasks, etc.) with permission-based authorization; (4) Data - Prisma ORM with a custom multi-tenant $extends extension; (5) Infrastructure - Auth, errors, pagination, email, AI. After 6 phases of refactoring, services are plain tree-shakeable functions, actions use a centralized wrapper, and dashboard pages use a single resolveOrgContext() call.

Q2: "How does multi-tenancy work?"

A: Every tenant-scoped table has an organizationId column. I built getTenantPrisma(orgId) using Prisma's $extends that intercepts ALL CRUD operations. On reads, it auto-appends WHERE organizationId = X. On creates, it injects organizationId. On updates, it strips organizationId to prevent cross-tenant migration. Cross-tenant data leaks are structurally impossible at the data layer. Every service function calls getTenantPrisma(organizationId) as its first step.

Q3: "Why did you refactor from static classes to plain functions?"

A: Static classes in TypeScript provide no runtime benefit. They add syntax noise, prevent tree-shaking, and create this binding confusion. Plain functions are the idiomatic pattern. All 15+ service files were converted from class XService { static async method() {} } to export async function method() {}. The result: simpler imports, better bundling, easier testing, and 53 files updated in one focused phase.

Q4: "What does the withAction wrapper do?"

A: withAction(handler, { paths }) eliminates try/catch boilerplate from all action files. It: (1) Calls the handler in a try/catch. (2) On success, revalidates specified cache paths. (3) Returns ActionResult<T> - either { success: true, data } or { success: false, error, code }. This reduced action file size by ~40% and ensures every action returns a consistent, type-safe response. The action file only defines the business logic - withAction handles error handling and cache management.

Q5: "How does the permission system work?"

A: A single requirePermission(orgId, permission) function handles everything: (1) Validates the JWT session. (2) Checks the user is an active member of this org. (3) Looks up their role's permissions in a static map. (4) Throws AuthorizationError if not allowed. 17 permissions across 5 resource types (finance, members, events, tasks, bhog, org, public). This replaced the old pattern of validateAccess(orgId, [ADMIN, TREASURER]) which mixed auth + membership + role checking in one call.

Q6: "How does resolveOrgContext simplify dashboard pages?"

A: Every dashboard page used to have 8-12 lines of identical boilerplate: resolve slug, check membership, derive isAdmin, derive isFestival. resolveOrgContext(orgSlug) does all of this in one call. It either returns { organization, member, isAdmin, isFestival } or throws (triggering 404). This reduced dashboard pages by 34 net lines across 9 pages, and each page is now focused on its unique rendering logic.

Q7: "How does multi-tenancy work?"

A: Every tenant-scoped table has an organizationId column. I built a custom Prisma Client extension using $extends that intercepts ALL CRUD operations. On reads, it auto-appends WHERE organizationId = X. On creates, it injects organizationId. On updates, it strips organizationId to prevent cross-tenant migration. Cross-tenant data leaks are structurally impossible at the data layer.

Q8: "How do you handle race conditions?"

A: For expense approval, we use updateMany with a WHERE clause that includes status: 'PENDING'. This is atomic at the DB level. If two admins approve simultaneously, only one gets count === 1. The second gets count === 0 because status is no longer PENDING, and we throw a ConflictAppError. No distributed locks needed, works perfectly with serverless.

Q9: "Why did you choose this tech stack?"

A: Next.js 14 for Server Components (zero-JS pages) + Server Actions (no API boilerplate). PostgreSQL for ACID compliance and complex relations. Prisma for type-safe queries and the $extends API. NextAuth for JWT strategy (stateless, serverless-friendly). Tailwind + shadcn for rapid, consistent UI. After refactoring, all services are plain functions - each choice optimizes for developer experience, performance, or scalability.

Q10: "How does the AI assistant work safely?"

A: Three safety layers: (1) Read-only architecture - the service only uses findMany and aggregation, never create/update/delete. (2) Mutation keyword blocking - questions with words like "add", "delete", "create" are immediately rejected. (3) Prompt injection guardrails - system prompt instructs Gemini to never execute commands. Data fed to Gemini is pre-aggregated, tenant-scoped facts.

Q11: "How does the slug/URL system work?"

A: Each organization has a unique slug. The database enforces uniqueness with @unique + @@index. In Next.js, the [orgSlug] dynamic route captures the URL parameter. A memoized getOrganizationBySlug() resolves slug to org (cached with React's cache()). If slug doesn't exist, 404 is returned. In V2, resolveOrgContext() wraps this resolution along with auth and membership checks.

Q12: "How do you handle the invitation system securely?"

A: crypto.randomBytes(32) generates a 256-bit unguessable token. 48-hour expiry. Strict email matching - the logged-in user's email must match the invite email. If wrong account is logged in, a warning is shown. If a member was previously archived, the system restores instead of creating duplicates. Admins can also skip email delivery and share the link via WhatsApp.

Q13: "What is the audit trail system?"

A: Every mutation calls record() from audit.service, which stores: entity type, entity ID, action (CREATE/UPDATE/APPROVE/etc.), before/after JSON snapshots, actor ID, and visibility level (INTERNAL or PUBLIC). The public transparency page filters for PUBLIC visibility only, showing citizens how funds were spent without exposing internal operations.

Q14: "Why not use raw SQL instead of Prisma?"

A: Prisma gives us: (1) Type safety - every query result is fully typed. (2) Schema as code - one file defines all tables, version-controlled. (3) Auto-generated client - no hand-written queries. (4) $extends - enabled the multi-tenancy pattern. (5) Migrations - schema changes sync automatically. (6) Works with plain functions - after refactoring, services are clean exports. Raw SQL would lose all of these benefits.

Q15: "What would you improve next?"

A: (1) E2E tests with Playwright for critical flows. (2) Real-time updates via WebSockets for live expense approvals. (3) PDF/Excel exports for financial reports. (4) CI/CD pipeline with GitHub Actions. (5) Mobile PWA for volunteer task management. (6) Complete migration from deprecated validateAccess() to requirePermission() across all services.

Q16: "How does the task module extraction work?"

A: Task logic was extracted from member.service.ts into a dedicated modules/tasks/task.service.ts. This follows the Single Responsibility Principle. The task service exports 6 plain functions: createTask(), getAllTasks(), getMyTasks(), updateTask(), updateTaskStatus(), deleteTask(), and getVolunteerWorkload(). Each service file now handles one domain. This made both files smaller, independently testable, and easier to navigate.

Q17: "Explain the 6 refactoring phases"

A: (1) Foundation - Created ActionResult<T>, requirePermission(), TenantContext pattern. (2) Services → Functions - Converted 15+ class-based services to plain exports (53 files). (3) withAction wrapper - Eliminated try/catch from all 11 action files. (4) resolveOrgContext - Replaced 8+ lines of boilerplate in 9 pages with one call. (5) Dead code cleanup - Deleted 4 files, achieved zero TS errors. (6) Tests passing - 25/25 tests, interview-ready codebase. Each phase built on the previous one.
