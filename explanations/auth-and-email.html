Lesson 5 — identity, signup, OTP and SES

First prove who someone is. Then decide what they may do.

Authentication answers “who are you?” Authorization answers “may you do this in this organization?” They are different locks and UTSAV needs both.

New account creation: verified before the User exists

Implemented now The sign-up page is deliberately two steps. Submitting name, email, phone and password does not create a User yet.

Create User + sign in
  1. Request code: requestSignupOtpAction validates details, rejects an already-used email/phone, hashes password and code, and stores a temporary PendingRegistration record.
  2. Protect pending data: the server puts a random enrollment token in an HttpOnly cookie. Another browser does not have it, so it cannot overwrite the pending password or personal details.
  3. Send email: src/lib/email.ts uses AWS SES v2 to deliver the code.
  4. Verify: verifySignupOtpAction checks expiry, attempts, hash and single use. It atomically consumes the exact code and creates the real User.
  5. Session: the page signs in using the newly verified password and redirects to the dashboard.

The temporary record expires after ten minutes. Resend changes only the code, expiry and attempt count; it does not silently replace account details.

Existing-user passwordless login

On /login, an existing user can request an OTP using requestOtpAction. The server stores a hashed EmailOtp, sends it through SES, and NextAuth verifies/consumes it before creating a session.

Important difference: Login OTP is for an account that already exists. An unknown email is directed to sign up; login OTP does not auto-create a blank account.

Why these protections exist

ProtectionProblem it prevents
HashingA database reader should not see usable passwords or OTPs.
Expiry + one-time useOld, delayed, or replayed codes should not work.
Attempt limitRepeated six-digit guessing is capped.
Rate limit + cooldownReduces inbox spam, abuse, and SES cost.
Enrollment cookieStops another browser from changing a pending signup’s password/profile.
Permission checkA valid account still cannot perform organization actions without membership and role permission.

Invitation flow

An authorized member creates OrganizationInvitation with invited email, role, random token and expiry. SES delivers an accept link. The accept page validates the pending record and recipient identity before creating/restoring an OrganizationMember row. An email message alone is never permission.

Known limitation

Email currently sends synchronously and UTSAV does not yet process SES bounce/complaint events. Before larger sending volume, configure SES event publishing, verify a webhook/consumer, suppress failing addresses, and show delivery state.

Interview answer

Say this

“UTSAV separates authentication from authorization. For a new account, the app stores a temporary hashed pending registration, emails an OTP through SES, and creates the real User only after atomic OTP verification. Existing users can use password or OTP login, but unknown OTP logins cannot create incomplete accounts. Every organization action then separately checks membership and permission.”
