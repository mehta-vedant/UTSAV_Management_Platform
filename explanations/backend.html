Lesson 4 — rules behind the screen

The backend is the trusted referee of UTSAV.

A person can alter browser requests. Therefore the server—not the button—checks input, identity, organization membership, permission and business rules before it changes long-term data.

Why UTSAV has server actions and an API route

Most UTSAV buttons are used only by UTSAV’s own web interface, so server actions are a compact fit: the form calls a server function without first designing a broad public REST API for every action. NextAuth is different: its library expects an HTTP endpoint contract, so src/app/api/auth/[...nextauth]/route.ts exists as an API route.

This is a design choice, not a rule that APIs are bad. If UTSAV later needs a mobile app or external partner integration, versioned and documented HTTP endpoints become useful because independent clients need a stable contract.

One real mutation from click to record

  1. Click: a member fills the expense form on the expenses dashboard and presses submit.
  2. Action: createExpenseAction in src/actions/expense.actions.ts receives the submitted values. It is an entry gate, not the entire business system.
  3. Validation: the action validates required fields and their shape before database work.
  4. Service: it calls createExpense in src/modules/finance/expense.service.ts.
  5. Authorization: the service uses requirePermission(organizationId, "finance:create"), which verifies session user, organization membership and the needed capability.
  6. Data write: Prisma creates a tenant-scoped Expense in PENDING state and finance audit logic records the event.
  7. Response/UI: the action returns a success/error outcome and the UI refreshes trusted server data.

Why not put all logic in the page?

Pages change frequently because presentation changes. Business rules deserve one reusable place: “only an approver can move a pending expense to approved” should be true whether the request came from a modal today or an API tomorrow. The service layer makes that rule testable and avoids duplicating it across screens.

Errors without leaking secrets

Expected errors include invalid form data, no session, no membership, no permission, expired invitation, unavailable email service or a record already changed by someone else. The user needs a clear safe message; developers need structured logs with context. Neither audience should receive database credentials, raw stack traces, OTP values or internal authorization details.

Read-only Gemini assistant

UTSAV includes a Gemini-oriented assistant path for finance-related questions. Its safe direction is intentionally narrow: classify question, gather bounded organization-scoped context, return an answer, and refuse mutation-style requests. It is an explanation aid, not a source of financial truth and not a tool that may write to the database.

Future improvement

If AI tools later perform actions, give them explicit allow-listed tools with the same authorization, tenant scope, audit logging and human confirmation as normal UI actions. Never give a model unrestricted database access.

Self-check

Say this aloud: “A server action is a convenient entry point for our web UI. It validates input, then a service owns the business rule. The service checks permission and tenant scope before Prisma writes PostgreSQL. The browser never gets to grant itself permission.”
