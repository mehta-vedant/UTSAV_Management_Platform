Lesson 6 — data is the app’s memory

PostgreSQL remembers facts. Prisma helps UTSAV ask for them safely.

A database is not mysterious: it is a carefully protected set of connected spreadsheets with rules. The rules are why finance and organization data remain understandable as the project grows.

Schema → migration → real database

prisma/schema.prisma is UTSAV’s blueprint. It describes what models exist, their fields, relations, enums and indexes. A migration converts a blueprint change into a repeatable database change. Without a migration, one developer’s database could disagree with production.

Other key models are EmailOtp and OtpRequestLimit for sign-in safety, OrganizationInvitation for pending membership, and EventAssignment/EventRegistration for event children.

How one query travels

  1. A page/service needs “approved expenses for organization A.”
  2. Prisma receives a typed query in TypeScript. An ORM is a translator between code objects and relational database tables.
  3. Prisma generates SQL (Structured Query Language), the language PostgreSQL understands.
  4. PostgreSQL uses tables/relations/indexes to locate matching rows and returns them.
  5. Prisma turns returned rows into TypeScript-friendly objects for the page/service.

Important: Prisma does not remove the need to think about data scope. The service must still use the right organization filter and authorization. An ORM reduces boilerplate; it cannot decide your security rules.

Why PostgreSQL, not MongoDB?

QuestionPostgreSQLMongoDBWhy UTSAV chose PostgreSQL
Basic shapeRelational tables connected by explicit relations.Document records, often JSON-shaped and flexible.UTSAV has many connected facts: user ↔ membership ↔ organization ↔ expense/event/audit.
RulesStrong constraints, foreign keys and transactions.Flexible documents; rules can be enforced in application/schema validation.Financial status, membership and audit relationships benefit from database-enforced structure.
Query styleExcellent joins and reporting across related tables.Excellent for document-shaped data that is often read as one aggregate.Reports and tenant-scoped relationships are central here.
Schema changesMore deliberate migrations.More flexible individual document shape.Deliberate changes are a benefit when data accountability matters.

When MongoDB could be better: if UTSAV stored highly variable event form answers, raw chat transcripts, or rapidly changing unstructured content where documents are usually fetched whole. Even then, it could coexist with PostgreSQL; it is not “bad,” just less natural for the core relational finance/membership model.

Financial honesty

Known limitation

UTSAV currently has financial records plus audit logging. That is useful accountability, but it is not a true double-entry ledger. A double-entry ledger records every movement with balanced debit and credit entries so totals can be reconciled. Do not claim that exists today.

Interview answer

“I chose PostgreSQL because UTSAV is relationship-heavy and accountability-sensitive: organizations, memberships, roles, donations, expenses, events and audit entries must remain connected. Prisma gives typed access and migrations, but the service layer still owns tenant filters and permissions. MongoDB would fit more flexible document data, but it would make the core relational/reporting model less natural.”
