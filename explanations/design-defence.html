06 — Defend the choices

Choose the simplest architecture that protects the important invariants.

A good answer is not “this is scalable.” It identifies the present constraint, names the trade-off, and describes the measurable trigger for change.

Current choices and rationale

Roadmap by evidence

Now

Finish SES production setup, test OTPs/invitations, monitor errors, back up the database and add receipt support.

At operational adoption

Fix parent-scoped event registration/assignment access, add SES bounce/complaint handling, observability, idempotency and richer audit/export workflows.

At measured load

Queue report/email jobs, cache safe read models, tune indexes and use database pooling. Do not add these speculatively.

At organizational scale

Extract a bounded worker or notification service only when team ownership and independent deployment needs outweigh monolith simplicity.

Counter-questions

“How do you prevent one organization from seeing another’s data?”

Authentication identifies the user; membership and role are checked per organization; tenant Prisma adds scope for covered organization-keyed models. Event assignments and registrations are a known parent-scope gap, so I would fix that before claiming universal coverage. This is still stronger than UI-only hiding.

“What is your biggest current limitation?”

Email feedback is not yet processed asynchronously, finance is not a full accounting ledger, and two event child models need explicit tenant scoping. I would fix those before distributed-system complexity.

“Why not microservices?”

They would split deployment and failure modes before there is a demonstrated scaling or team-boundary need. Modules provide a migration path while transactions remain simple today.
