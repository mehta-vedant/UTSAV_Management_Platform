Lesson 3 — what users see and touch

The frontend is the part of UTSAV that turns facts into a usable screen.

It is not “just design.” A good frontend tells the right story, collects input clearly, shows errors honestly, and asks the backend to make changes without ever owning security decisions.

Components, props and state

A component is a reusable UI piece, like a Lego brick. A modal, sidebar or donation form can be a component. Props are information a parent gives to a component, like handing a waiter the table number. State is changing local memory: “is this modal open?”, “what has the person typed?”, “is submission loading?”

Example: an ExpenseForm component may receive an organization ID and permitted categories as props; its state holds the current amount text and whether the submit button is busy. It sends submitted values to the server action. It must not decide that the person is allowed to approve finance; that belongs on the server.

Next.js server versus client components

Next.js App Router renders components on the server by default. A server component can securely read the session and fetch data before HTML reaches the browser. A client component, marked with "use client", runs browser-side JavaScript for interactive things such as typing, tabs, dialogs and click handlers.

Rendering means turning component code + data into visible HTML. Hydration means browser JavaScript connects interactive behavior to HTML the server already sent. This gives a fast initial page and then usable controls.

Trace one dashboard page

  1. URL: the person opens /ganesh-utsav/dashboard/expenses.
  2. Route file: Next.js finds the matching page under src/app/[orgSlug]/dashboard/expenses/.
  3. Context: server-side code reads orgSlug = "ganesh-utsav", identifies the signed-in user, and resolves the organization safely.
  4. Data: a service/Prisma query loads only appropriate expense data for that organization and role.
  5. HTML: React renders headings, totals, table rows and an add-expense entry point.
  6. Interaction: the browser hydrates client pieces; the person can open a form, type details, and submit.
  7. Mutation: submission calls a server action. On success the page is refreshed/revalidated so the displayed list comes from trusted server data.

Forms are conversations, not just fields

A good form explains what is needed, prevents obvious mistakes early, disables duplicate submission while busy, and reports success/failure plainly. But browser validation is for user experience, not security: anyone can bypass it with custom HTTP requests. The same input must be validated and authorized again in the server action/service.

Interview answer

“The frontend is built with React inside Next.js App Router. Route folders map URLs to pages. Server components handle initial protected data loading; client components are reserved for interaction such as forms and modals. The browser can validate for convenience, but the server action and service are the authority for all data changes.”
