Practical release readiness

What must happen before you trust real users with UTSAV.

Code being on GitHub is not the same as a feature being live. This checklist separates code changes, database changes, cloud configuration, and real-world tests.

1. Required before deploying the current signup change

  1. Apply the database migration. The new signup flow needs the PendingRegistration table. Run npx prisma migrate deploy against the production database during deployment.
  2. Set the production environment variables. Vercel needs the database URL, NextAuth secret/URL, canonical app URL, AWS SES region, AWS access key, AWS secret key, and verified sender email.
  3. Redeploy after setting variables. Environment variables are read by the server deployment, so a new deployment is required.
  4. Use a real inbox to test. Sign up → receive OTP → verify → reach dashboard. Then test password login, existing-user OTP login, invitation sending, and invitation acceptance.

4. Best next engineering work, in order

PriorityWhy it is nextWhat “done” means
1. Event child tenant scopingIt is the most important known correctness/security gap.Assignments and registrations are always queried through a tenant-verified parent event, or carry a constrained organization ID.
2. SES bounce/complaint feedbackProduction access lets SES send, but delivery can still fail.SES events reach a verified handler; permanently failing addresses are suppressed and admins can see delivery state.
3. Financial evidence + idempotencyMoney records need receipts and protection from duplicate retries.Expense receipts are stored securely; repeat submission keys cannot create duplicate financial records.
4. Monitoring and backupsYou need to know when production fails before users report it.Error tracking, structured logs, database backup/recovery plan, and basic alerts exist.
Do not rush into

Microservices, Redis caching, queues, or a complicated public API just because they sound advanced. Build them when measured traffic, slow work, retry needs, or separate-team ownership gives a real reason.

Interview line

“Before calling a feature live, I separate application code from operational readiness: migration applied, secrets configured, sender identity verified, real inbox tests passed, and failure monitoring planned.”
