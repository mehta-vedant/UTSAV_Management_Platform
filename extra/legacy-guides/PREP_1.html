1 · Project Overview

UTSAV is a production-grade multi-tenant organization governance platform that digitizes the operations of large-scale cultural organizations and festivals (pavilions, committees, clubs). It replaces manual ledgers and WhatsApp groups with a high-integrity "digital twin" of an organization.

It began as a Festival Management System and evolved into a general Organization Governance Platform: manage multiple events, hundreds of members, invitations, tasks, bhog/prasad sponsorship, and a financial engine — all with strict data isolation between organizations.

One-line summary you can say out loud:
"UTSAV is a Next.js 14 modular-monolith that gives each cultural organization (a 'pavilion') its own isolated workspace — with RBAC, a decimal-safe financial ledger with approval workflows, event lifecycle management, token-based member onboarding, public transparency pages, and a read-only Gemini-powered admin assistant — secured at three layers: middleware, a service-level permission engine, and a Prisma client extension that force-injects the tenant ID into every database query."

Feature surface

Multi-tenant core
  • Virtual "Pavilions" (Festivals, Clubs) with hard 10-org-per-user limit
  • Logical row-level isolation via getTenantPrisma
  • Role-based access control (Admin / Treasurer / Committee / Volunteer)
  • Secure "Danger Zone" org deletion (transactional)
High-integrity finance
  • Donations (income) & Expenses (outflow) tracking
  • Approval workflow: PENDING → APPROVED / REJECTED
  • Race-condition-safe approvals (optimistic updateMany guard)
  • Decimal-safe balances, utilization %, overspend alert
Events & people
  • Event lifecycle: PLANNED → ACTIVE → COMPLETED
  • Soft-delete archiving for audit preservation
  • Smart rostering (filters archived members), tasks, attendance
  • Bhog (prasad) sponsorship with offering windows
Onboarding & transparency
  • Token-based invitations (48h expiry, email matching)
  • WhatsApp/copy-link sharing, email via Resend
  • Public donation / transparency pages per festival
  • Read-only Gemini admin assistant for natural-language queries

2 · Problem & Product

The problem being solved

Large cultural festivals run on chaotic, manual tooling: paper ledgers, shared spreadsheets, group chats. The consequences:

  • No financial integrity — donations/expenses recorded ad-hoc; no audit trail, no approval, no reconciliation.
  • No separation of duties — one person controls everything; mistakes and misuse are invisible.
  • No structured member management — rosters, roles and task assignments live in chat history.
  • No public trust — donors can't see how funds are used.

Product decisions that followed

PainProduct response in UTSAV
Financial chaosStructured Donation/Expense records, Decimal money, approval workflow, audit logs, dashboards with target-vs-utilized.
No trust in committeesRBAC separation: Treasurer approves money; Committee manages events; Volunteers update their own tasks.
Multiple organizationsMulti-tenant architecture — one deployment, many isolated orgs ("pavilions").
Manual onboardingEmail + token invitations with 48h expiry, email-match enforcement, WhatsApp sharing, optional skip-email.
Donor trustPublic transparency pages: only approved expenses + donations shown, festival-mode guard.

The layered request path (narrated)

1 · Client form submit→ 2 · Server Action (zod)→ 3 · Service (permission)→ 4 · getTenantPrisma→ 5 · WHERE organizationId=…→ 6 · PostgreSQL→ 7 · revalidatePath→ 8 · toast + re-render

Every mutation returns a uniform ActionResult envelope and revalidates the affected cache paths, so the UI stays fresh without a full-page reload.

4 · Tech Stack + Justification

Every choice below is justified by a concrete project need. "Because it's popular" is never the reason — each is tied to multi-tenancy, financial integrity, type safety, or delivery speed.

4.1 Runtime & framework

TechnologyRoleWhy (justification)
Next.js 14.1 (App Router) Full-stack framework: UI + API + server logic Server Components keep data fetching on the server (no client round-trips for reads). Server Actions replace a hand-rolled REST/Express API for mutations, cutting boilerplate dramatically. File-based routing models the multi-tenant URL space natively (/[orgSlug]/dashboard/…). revalidatePath gives granular cache invalidation after writes. Single language across DB and UI.
TypeScript 5 (strict) Static typing everywhere Money is Decimal, roles are enums, actions return discriminated unions. Strict mode + the Prisma-generated types turn a class of DB/UI contract bugs into compile errors. The refactor Phase 5 goal was literally "0 TS errors."
React 18 UI library The framework React that Next 14 requires; enables RSC, use(), streaming and concurrent features.

4.2 Data & ORM

TechnologyRoleWhy (justification)
Prisma 5.10 ORM / type-safe query builder The centerpiece enabler: Prisma's $extends client-extension API powers getTenantPrisma, the tenant-isolation backbone (see §6). Generated client = zero raw SQL in the app. Declarative schema is a single source of truth for the DB and the types. Migration workflow (db push in dev, migrate deploy in prod).
Decision: the team evaluated Drizzle/Kysely/raw SQL and kept Prisma — the tenant-extension mechanism outweighs the smaller runtime footprint. See UTSAV_PRISMA_DECISION.html.
PostgreSQL Database Relational integrity (composite unique keys, FKs with cascade), exact Decimal(12,2) money (no float drift), native JSON for audit snapshots and feature flags, robust GROUP BY/aggregation for the finance dashboard, and managed serverless hosting (Neon/Supabase/Railway) that fits a Vercel deployment.

4.3 Auth & security

5.3 Why these modeling decisions?

Nullable userId on OrganizationMember: you can invite an email address that has no account yet. The member row exists at invite-acceptance time only, but the schema already allows "person without a user." On acceptance the row is linked or restored.
Two named relations for Expense: a single memberId could let someone "approve their own expense." The schema + service layer together enforce separation of duties.
Composite uniques over manual checks: @@unique([email, organizationId]) means the database — not just app code — rejects duplicate invites/memberships.
Soft-delete isArchived everywhere: festivals must answer "what did we spend last year?" years later. Records are archived, never destroyed; every archived row keeps archivedAt/archivedById.

6 · Tenant Isolation (the security backbone)

UTSAV uses logical row-level isolation instead of one-database-per-tenant. A Prisma client extension force-injects organizationId into every operation on tenant models, so even a developer mistake can't leak data across organizations.

6.1 The mechanism — getTenantPrisma(organizationId)

File: src/lib/access-control.ts:176-243. For every model on an allowlist it intercepts all operations and:

  • Reads (findMany, findFirst, update…): merges organizationId into where.
  • Creates (create, createMany, upsert): injects organizationId into the payload (arrays handled too).
  • Updates: deletes any caller-supplied organizationId from the payload — you can never move a row across tenants.
export const getTenantPrisma = (organizationId) => {
  if (!organizationId) throw new InvariantError("Organization context is missing.");
  return prisma.$extends({
    query: { $allModels: {
      async $allOperations({ model, operation, args, query }) {
        const tenantModels = ["Donation", "Expense", "OrganizationMember", "BhogItem",
          "Volunteer", "Event", "VolunteerTask", "AuditLog",
          "EventAssignment", "EventRegistration"];
        if (tenantModels.includes(model)) {
          const a = args;
          if (a.where) a.where = { ...a.where, organizationId };
          else if (operation !== "create") a.where = { organizationId };
          if (operation === "create" && a.data) a.data = { ...a.data, organizationId };
          if (operation === "createMany" && a.data) { /* inject into each item */ }
          if ((operation === "update" || "updateMany") && a.data?.organizationId)
            delete a.data.organizationId;   // can't change tenant
          if (operation === "upsert") { /* inject into create, strip from update */ }
        }
        return query(args);
      }
    }}
  });
};

6.2 Defense in depth (4 layers)

1 · middleware.ts (JWT gate)→ 2 · layout validateAccess (membership)→ 3 · service requirePermission (RBAC)→ 4 · getTenantPrisma (WHERE org=…)
  1. Middleware — withAuth blocks unauthenticated access to /dashboard/* and /[slug]/dashboard/*.
  2. Layout-level — the org dashboard layout calls validateAccess(organization.id): you must be a non-archived member of that exact org.
  3. Service-level RBAC — every mutation re-checks the permission for the action.
  4. ORM-level — getTenantPrisma makes cross-tenant queries structurally impossible.
Why not database-per-tenant? One shared DB with row-level scoping costs far less (no per-tenant connection pools), is operationally simpler to migrate/backup, and — combined with the Prisma extension — is as safe for this scale. Physical isolation is reserved for larger compliance requirements.
Known subtlety (be ready to discuss): OrganizationInvitation is not on the allowlist, so invitation writes only work because callers pass organizationId explicitly. Also, a raw tenantPrisma.organizationInvitation.findMany() without a filter would not be auto-scoped. In practice the accept-invite flow uses the global prisma keyed by the token, which is safe.

7 · Authentication & Security

7.1 Flow

Signup: zod → bcrypt(12) → User row→ Login: CredentialsProvider → bcrypt.compare→ JWT callback copies id+phone into token→ Session callback exposes them→ Layouts re-verify via getServerSession
  • Session strategy: "jwt" — stateless, horizontally scalable. Roles are never stored in the JWT; they're fetched from the DB on every request in resolveAccess(). Promotion/demotion/archival therefore takes effect immediately and can't be cached stale inside a token.
  • Credentials provider (email + password). Google OAuth keys exist in .env.example but no OAuth provider is wired yet.
  • Enumeration defense: generic "Invalid credentials" for wrong password, unknown email, or passwordless accounts.
  • Redirect hardening: redirect callback only allows relative or same-origin URLs, else falls back to /dashboard.
  • CSRF: handled by NextAuth's double-submit tokens; Server Actions get Next.js origin protection.
  • Cookies: NextAuth defaults — __Secure-next-auth.session-token over HTTPS, httpOnly, sameSite=lax.
  • Passwordless users: User.password is nullable — someone invited before registering can set a password later.

7.2 Prisma singleton

const globalForPrisma = global as { prisma: PrismaClient };
export const prisma = globalForPrisma.prisma ||
  new PrismaClient({ log: ["query"] });
if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;

The global pattern prevents connection exhaustion during hot reloads in dev.

8 · Role-Based Access Control (RBAC)

RBAC is a fine-grained permission system (17 permissions), not coarse role-gating. Roles map to permission lists in src/lib/access-control.ts:26-73.

Separation of duties is the point: a Treasurer can approve finance but cannot manage events; a Committee member can manage events but cannot approve expenses. No single non-admin role can run an entire operation unchecked. Verified by tests.

Enforcement points

  • requirePermission(orgId, perm) — the modern fine-grained check (finance, assistant).
  • validateAccess(orgId, roles[]) — marked deprecated, still used by events/tasks/bhog/members services; scheduled for removal.
  • resolveAccess() — shared core: session → membership lookup by userId OR email with isArchived: false.
  • Ownership check: updateTaskStatus — a VOLUNTEER may only update tasks where assignedToId === member.id.
  • Last-admin guard: demoting/archiving the final active ADMIN is blocked with a "Critical Security Violation" message (member.actions.ts).
Rescue tooling: rescue.js / rescue_admins.js (repo root) scan for organizations left with zero active admins and auto-promote the first non-archived member — self-healing for a "locked org" incident.

9 · Financial Engine (high-integrity ledger)

UTSAV implements a single-entry, cash-basis ledger: Donation rows are income, Expense rows are outflow, and balances are computed with Prisma.Decimal arithmetic. There are no journal entries or T-accounts — the design intentionally matches how a festival committee thinks (income vs spend vs target).

9.1 Balance formula

getOrganizationFinancialOverview  // financial.service.ts:82-133
totalCollection = openingBalance + nonSponsorshipDonations + sponsorships
remainingBalance = totalCollection − totalExpenses(APPROVED only)
rawUtilization  = totalExpenses / totalCollection × 100
isOverspent     = rawUtilization > 100
  • Income split: SPONSORSHIP category is counted separately from general donations.
  • Expenses: only status = APPROVED and isArchived = false hit the ledger; PENDING tracked separately as an alert.
  • Fallback: openingBalance ?? budgetTarget for orgs created before the finance split migration.

9.2 Approval workflow + race-condition safety

The heart of integrity is optimistic concurrency via a guarded atomic update:

const result = await tenantPrisma.expense.updateMany({
  where: {
    id: expenseId,
    organizationId,                    // redundant safety
    status: ExpenseStatus.PENDING,     // compare-and-set
    isArchived: false,
  },
  data: { status: APPROVED, approvedById: member.id,
          approvedAt: new Date(), processedAt: new Date() },
});
if (result.count === 0)
  throw new ConflictAppError("This expense was already processed.");
Why updateMany+count instead of a transaction? Two admins clicking "approve" simultaneously: the second updateMany matches 0 rows because status is no longer PENDING — the DB's atomic compare-and-set wins the race, and the loser gets a clean 409 "already processed". This is simpler and safer than a read-then-write transaction for a single-row state change. The README's "$transaction for everything" claim predates this pattern.

9.3 Decimal-safety

  • Money stored as Decimal(12,2), converted via new Prisma.Decimal(amount.toString()) (string round-trip avoids float drift).
  • Comparisons use .gt(0), .lte(0), .isZero(), .dividedBy() — never raw JS arithmetic.
  • Zod enforces amount: z.number().gt(0) at the action boundary; services re-validate (title ≤ 200, donorName ≤ 100).

9.4 Audit logging

Every financial mutation writes an AuditLog row with before/after JSON snapshots (best-effort, not in the same transaction). Expensive workflow, donations and bhog all record an audit entry.

9.5 Event vs organization spending

organization-financial.service.ts splits spend: eventId = null is org-level, per-event rows compute remaining = budgetTarget − spent. Event summary: available = budget + collections; remaining = available − approvedExpenses.

10 · Events Lifecycle & Rostering

  • Plan: createEvent defaults status = PLANNED.
  • Activate / Complete: the UI (EventStatusSelector) passes status through the generic updateEvent.
  • Archive (soft-delete): deleteEvent is ADMIN-only and sets isArchived: true — history (finances, attendees) survives for audits.
  • Rostering: getEventWithDetails deliberately excludes archived members from the team list; assignments use the composite-unique EventAssignment table.
  • Linked money: Donation.eventId / Expense.eventId (migration 003) drive per-event financial summaries and the transparency timeline.
Two archive concepts: status = ARCHIVED (a lifecycle state the selector can set) vs isArchived = true (the ADMIN-only soft-delete). The service type doesn't formally declare status in UpdateEventInput — the UI passes it as any. A known wart to mention honestly.

11 · Invitations & Onboarding (token-based)

ADMIN invites email+role→ token = randomBytes(32).hex→ expiresAt = +48h→ email (Resend) or share link→ /accept-invite?token=…→ email-match → membership created
  1. 256-bit CSPRNG token (crypto.randomBytes(32)), stored with a @unique constraint.
  2. 48-hour expiry enforced in the accept flow.
  3. Email matching is the real gate: the server action throws "Account mismatch. This invite is for X…" unless session.user.email === invite.email (case-insensitive). This prevents account hijacking via shared links.
  4. Membership dedupe: if the user is already an active member, redirect — you can't overwrite a role through an invite.
  5. Stale-JWT guard: the user is re-fetched from DB by email before creating membership.
  6. Event auto-assign: invites bound to eventId upsert an EventAssignment on acceptance.
  7. Archived restore: accepting as a previously-archived member restores them with the invite's role.
  8. skipEmail supports copy-link / WhatsApp onboarding; email gracefully degrades without RESEND_API_KEY.

12 · Server Actions Architecture

12.1 The uniform contract

// src/lib/action-response.ts
type ActionResult<T> =
  | { success: true;  data: T;   error?: undefined; code?: undefined }

14 · AI Admin Assistant (read-only Gemini)

  • Read-only by design: mutation intents are blocked (MUTATION_KEYWORDS → UNSUPPORTED_MUTATION), and the whole assistant requires at least finance:read for financial questions.
  • Intent classification: Gemini classifier with a deterministic keyword fallback (spending → EXPENSE_BREAKDOWN, donors → DONATION_SUMMARY, pending approvals → PENDING_EXPENSES, event budget → EVENT_FINANCIALS).
  • No-key degradation: without GEMINI_API_KEY, generateGeminiText returns null and the fallback answers kick in.
  • Prompt-safety tests assert the prompt contains tenant-scoped facts, never leaks "password"/"token", and ignores injection attempts.

15 · Public Transparency Layer

Public pages are unauthenticated but still tenant-scoped (the organizationId comes from the resolved slug — getTenantPrisma still applies). assertFestivalMode blocks club tenants from festival public pages.

  • Only APPROVED expenses are ever public; pending/rejected are never exposed.
  • Financial overview hides sensitive fields: exposes only publicFundraisingTarget, never openingBalance/budgetTarget (test-verified).

21 · Interview Q&A

Q1 · How does UTSAV prevent one organization from seeing another's data?

Three enforcement layers plus an ORM-level guarantee: (1) middleware gates authenticated dashboards; (2) the org-dashboard layout calls validateAccess(orgId) so you must be a non-archived member; (3) every service re-checks fine-grained permissions via requirePermission. The strongest layer is getTenantPrisma(orgId) — a Prisma $extends client that rewrites every query/write on tenant models to include organizationId, injects it into creates, and strips it from updates so rows can't be moved between orgs. Even a developer error can't leak data.

Q2 · How do you guarantee a donation/expense is never double-processed?

Approvals use an atomic compare-and-set: expense.updateMany({ where: { id, organizationId, status: PENDING, isArchived: false }, data: { status: APPROVED, ... } }). If two requests race, only one matches the status: PENDING guard; the loser sees count === 0 and throws a 409 ConflictAppError("already processed"). This is simpler and safer than a read-modify-write transaction for a single-row transition.

Q3 · Why is money stored as Decimal and not a JS number?

IEEE-754 floats can't represent most decimal fractions exactly (0.1 + 0.2 ≠ 0.3), which corrupts accounting. The schema uses Decimal(12,2) via @db.Decimal, and services convert with new Prisma.Decimal(amount.toString()) — a string round-trip that avoids float artifacts. All comparisons use .gt(0), .isZero(), .dividedBy() rather than raw arithmetic.

Q4 · Why JWT sessions instead of database sessions?

JWT is stateless: no session-table lookup per request, which scales horizontally on serverless functions. The important detail is that we don't cache roles in the token — every request re-resolves membership and role from the DB in resolveAccess(). So a promotion, demotion, or archival takes effect immediately and can't go stale inside a token.

Q5 · How is the invite system secure?

A 32-byte CSPRNG token (256 bits) is unguessable; it expires in 48 hours; it's unique in the DB. The critical control is email matching: the accepting server action throws an "Account mismatch" error unless the logged-in email equals the invited email. Additionally, if the user is already an active member we redirect rather than overwriting their role, and archived members are restored with the invite's role. Email delivery via Resend degrades gracefully so link-sharing still works.

Q6 · Explain the architecture in one paragraph.

UTSAV is a modular monolith on Next.js 14's App Router. Server Components read data through domain services in src/modules, which check RBAC through access-control.ts and query a tenant-scoped Prisma client that force-injects organizationId. Mutations are Server Actions in src/actions that validate with Zod, call services, and return a uniform ActionResult while revalidating the affected cache paths. Data lives in one PostgreSQL database with row-level tenant isolation, soft-delete archiving, and Decimal money.

Q7 · What was the most interesting refactoring you did?

Phase 3 — introducing withAction. Every action previously had its own try/catch, error-mapping, and revalidate calls (two different patterns existed). We centralized that into one wrapper plus a discriminated-union response type, deleted hundreds of lines, and made every mutation follow the same contract. It was low-risk, high-leverage cleanup that the test suite protected.

Q8 · How would you scale this beyond one database?

First add Prisma Accelerate/pgbouncer for connection pooling. For genuinely massive multi-tenancy, shard by tenant with a routing layer keyed on organizationId — the extension architecture already isolates queries so shard keys are the only new concern. Keep logical isolation until per-tenant compliance (e.g., data residency) requires physical DB-per-tenant, which the getTenantPrisma seam makes swap-in-able.

Q9 · What security weaknesses exist?

Honestly: invitation tokens are stored raw (should be hashed), there's no login rate limiting, no CSP/security headers (no next.config.js), and npm run lint fails because ESLint isn't installed. I'd fix rate limiting first (Upstash), then hash tokens, then headers + a CI pipeline with the tenant-isolation integration tests.

Q10 · Why Server Actions instead of a REST/GraphQL API?

For a server-rendered app the REST layer was mostly boilerplate: route handlers, fetch wrappers, serialization, client state management. Server Actions are typed end-to-end, callable directly from components, run on the server with full DB access, and integrate with revalidatePath for cache correctness. The downside — no standalone API for third parties — doesn't matter for this product; the only API route is the NextAuth catch-all.

Q11 · How do you test this system?

Vitest + React Testing Library, tests co-located with source. We unit-test pure logic (permission matrix, prasad windows, pagination), service behavior (the expense approval race-guard and audit logging via mocked tenant client), action validation shapes, and one component. All 25 tests pass. The gap: no integration tests against real Postgres, no E2E, no CI — the roadmap from the redesign doc is a test pyramid with Playwright and a tenant-isolation integration suite.

Q12 · What would you add next?

Three things: (1) surface the real AuditLog on the transparency page so public trust is backed by the audit trail rather than a derived ledger; (2) finish migrating the legacy raw-try/catch actions to withAction; (3) add OAuth (Google provider already staged) and a proper CI/CD pipeline. Then the test pyramid expansion and rate limiting for hardening.
