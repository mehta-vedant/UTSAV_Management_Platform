A · What HLD and LLD mean for this project

HLD (High-Level Design) — the blueprint
  • System context: users, browser, Vercel, PostgreSQL, Resend, Gemini.
  • Architecture style: modular monolith on Next.js 14.
  • Component decomposition: routes, actions, services, data layer.
  • Request flows: read, mutate, public, invite, assistant.
  • Deployment topology + quality attributes (security, integrity, scale).
LLD (Low-Level Design) — the code
  • Module map with exact file paths.
  • Every exported function: signature, permission gate, audit behavior.
  • Component inventory with props.
  • State machines (expense, event, task, bhog).
  • Sequence diagrams for the critical paths.
  • Database schema, enums, indexes, migrations.
Important framing: UTSAV's services are plain functions, not classes — this was an intentional Phase-2 refactor (see §R). The only real class hierarchy is the AppError family in src/lib/errors.ts. React components are functions too. When we say "classes implemented," the honest answer is: domain logic is a set of 58 exported functions organized into 6 modules, plus one error class hierarchy. This is a feature, not an omission — details in §I.

G · HLD Improvements (blueprint-level)

G1 · Connection pooling & Prisma Accelerate
Serverless functions create many short-lived connections. Add Accelerate/pgBouncer in front of Postgres to avoid connection limits at scale. Low effort, immediate ceiling lift.
G2 · Add caching layers
Public transparency pages are read-heavy and rarely change. Options: (1) Next.js ISR with a short revalidate window keyed on org slug; (2) Redis (Upstash) cache for public financial aggregates keyed public:fin:{orgId}, invalidated on donation/expense mutations. Reduces DB load and page latency.
G3 · Async jobs for non-critical work
Resend emails and audit writes are fire-and-forget in code. Introduce a queue (Inngest / QStash) so invite emails + audit logs are durable and retryable without blocking the mutation response.
G4 · Read replicas / CQRS-lite
Route dashboard reads to a read replica; writes to primary. The public/transparency read-models already are a quasi-CQRS — formalize them as materialized read tables if scale demands.
G5 · Rate limiting at the edge
Upstash Ratelimit in middleware.ts for auth endpoints and public forms (bhog sponsorship, register) to stop brute force and spam.
G6 · Multi-region / DR
Postgres on Neon (built-in branching/point-in-time) + Vercel regional deployment. Document RPO/RTO. Logical multi-tenancy makes a "restore one tenant" story via Neon branch feasible.
G7 · Observability platform
Add Sentry for error tracking + OpenTelemetry traces; export Prisma query spans. Turn the AuditLog into the domain-event backbone.
G8 · Data residency / compliance
If tenants demand regional storage, the getTenantPrisma seam allows sharding by tenant region (each shard a DB, extension picks the client) — a clean upgrade path from logical to physical isolation.

I · "Classes" Implemented — the honest answer

Design decision (Phase 2 refactor): every domain service was converted from static classes to plain exported functions. Why? Static classes in TS are just function namespaces with extra ceremony; plain functions are tree-shakeable, trivially mockable in Vitest (vi.mock), have no hidden this context, and reduce indirection. The modules become collections of functions, and the dependency injection is explicit (org id + data passed as parameters).

I.1 The only real class hierarchy — error taxonomy

class AppError extends Error
  ├─ code: AppErrorCode      // "AUTHENTICATION_REQUIRED" | "NOT_AUTHORIZED" | ...
  └─ status: number          // HTTP status

class AuthenticationError extends AppError   // 401 AUTHENTICATION_REQUIRED
class AuthorizationError  extends AppError   // 403 NOT_AUTHORIZED
class ValidationAppError  extends AppError   // 422 VALIDATION_ERROR
class NotFoundAppError    extends AppError   // 404 NOT_FOUND
class ConflictAppError    extends AppError   // 409 CONFLICT
class InvariantError      extends AppError   // 500 INVARIANT_VIOLATION

// normalizer maps unknown → { code, message }
normalizeError(error, fallback)
   ZodError → VALIDATION_ERROR(first issue) · AppError → passthrough
   Error    → UNKNOWN_ERROR · else → fallback

I.2 Everything else is functions — the "virtual classes"

If an interviewer asks "what classes are implemented," give both answers:

  1. Literal: the AppError hierarchy; React function components; that's it.
  2. Conceptual: the 6 modules are the logical "classes" of the domain — core, finance, events, tasks, festival, assistant — each a cohesive set of functions with a clear responsibility. The per-module function groups behave like classes with static methods, minus the ceremony.

N · State Machines (LLD)

Expense: PENDING ─approve/reject─▶ APPROVED / REJECTED (approval uses atomic compare-and-set; transitions locked by guard) Event: PLANNED ─▶ ACTIVE ─▶ COMPLETED ─▶ (optional) ARCHIVED deleteEvent() sets isArchived=true (soft-delete, ADMIN only) Task: PENDING ─▶ IN_PROGRESS ─▶ COMPLETED (VOLUNTEER only own tasks) Bhog: PENDING ─▶ PREPARED (sets approvedAt + preparedAt) Org: ACTIVE ─endFestival─▶ ENDED (endedAt + endedById) Member: active ↔ archived (isArchived) · last-admin removal blocked Invite: pending ─accept─▶ accepted (48h expiry window)

O · Sequence Diagrams (critical paths)

O.1 Tenant-isolated query

Client ──▶ Server Action ──▶ Service ──▶ requirePermission(orgId, perm) Service ──▶ getTenantPrisma(orgId) // $extends client getTenantPrisma ──▶ interceptor: merge { organizationId } into where inject into create/createMany/upsert DELETE organizationId from update payloads interceptor ──▶ Prisma ──▶ PostgreSQL Service ◀── rows (guaranteed same-org only)

O.2 Expense approval race

Actor A ──approve──▶ updateMany(where:{id, orgId, status:PENDING}) Actor B ──approve──▶ updateMany(where:{id, orgId, status:PENDING}) Postgres: one UPDATE matches 1 row (A wins, count=1) B: count=0 ──▶ throw ConflictAppError("already processed") ──▶ 409 toast

O.3 Invite acceptance (server-side gate)

acceptInviteAction(token) 1. invite = findUnique({token}) // null → invalid 2. accepted? expired? // short-circuit screens 3. session required // else redirect signup w/ email 4. dbUser = fetch fresh by email // stale-JWT guard 5. existing member by userId OR email // active → redirect (no overwrite) 6. email = invite.email (ci) ? // MISMATCH → throw 403 "Account mismatch" 7. create member OR restore archived (role=invite.role) 8. invite.eventId → eventAssignment.upsert 9. invite.accepted = true ──▶ redirect org dashboard

R · Design Decisions (HLD + LLD together)

LayerDecisionRationale
HLDModular monolith, not microservicesOne deployable, shared types, tenant boundary enforced in-process. Microservices add latency + distributed-tx pain with zero benefit at this scale.
HLDLogical multi-tenancy (shared DB, row scoping)Cost + ops simplicity; safety bought by the Prisma $extends interceptor that makes cross-tenant access structurally impossible.
HLDServer Actions instead of REST APITyped end-to-end, no fetch/serialization boilerplate, revalidatePath cache correctness. Only public API route is NextAuth.
HLDRSC-first data fetchingNo client round-trip for reads; public pages can be partially static.
HLDJWT stateless sessionsHorizontal scale; roles re-fetched per request so changes are instant (no stale claims).
HLDPostgreSQLDECIMAL money, JSONB audit, composite uniques, aggregates, managed serverless hosting.
LLDPlain functions over service classesTree-shakeable, mockable, no this context, explicit DI via params. Phase-2 refactor.
LLDwithAction + ActionResult unionOne success/failure contract for every mutation; central error normalization; automatic revalidation.
LLDFine-grained 17-permission RBACSeparation of duties: Treasurer approves money, Committee runs events, Volunteer updates own tasks only.
LLDCompare-and-set expense approvalAtomic updateMany with status:PENDING guard beats a transaction for single-row transitions; 409 on race loss.
LLDDecimal(12,2) + Prisma.Decimal mathFloats corrupt money; string-round-trip conversion avoids drift.
LLDSoft-delete (isArchived) everywhereAudit preservation for year-over-year transparency.
LLDToken invites: 32B CSPRNG + 48h expiry + email matchUnguessable, bounded exposure, hijack-proof via strict email equality (server-side).
LLDTransactions reserved for org create/deleteOnly multi-row invariants need true atomicity; single-row finance uses guarded updates.
LLDZod at boundary + manual service guardsDefense in depth; rules can't be bypassed by a new entrypoint.
LLDRead-model public services (quasi-CQRS)Public pages read pre-filtered, safe projections; only APPROVED data ever leaves the org.
LLDReact cache() for slug→org lookupOne DB hit per request even when many components resolve the same org.
LLDEnv-gated adapters (Resend, Gemini)Missing keys degrade gracefully; app stays fully functional for core use.
LLDIdempotent seed via upsertsRe-runnable dev bootstrap without duplicate-constraint failures.
