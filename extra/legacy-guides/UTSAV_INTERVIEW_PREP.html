1 Project Overview

What is UTSAV?

UTSAV is a production-grade web application built to help organizations manage large-scale cultural events like Ganeshotsav festivals and community clubs. Think of it as a specialized management tool that handles:

  • Money tracking - Who donated how much, what was spent where, approval workflows for expenses
  • Event management - Schedule ceremonies, assign team members, track registrations
  • Volunteer coordination - Create tasks, assign them, track completion
  • Public transparency - Let the public see how funds are used (without logging in)
  • AI-powered insights - Ask questions like "How much have we spent on decoration?" in plain English

The key word is "multi-tenant" - one codebase serves hundreds of different organizations, and each organization's data is completely isolated from others.

2 Key Concepts (Learn Before Interview)

What is an ORM? (Object-Relational Mapper)

Plain English: An ORM lets you write code like prisma.donation.findMany() instead of writing raw SQL like SELECT * FROM "Donation" WHERE "organizationId" = 'abc123'. It maps your code's objects/tables to actual database tables. You define your schema in code, and the ORM generates the SQL for you.

Prisma is the specific ORM used in UTSAV. It has 3 parts:

  1. Prisma Schema (prisma/schema.prisma) - A file where you define all your database tables, their fields, and relationships. This is your "database blueprint."
  2. Prisma Client - Auto-generated TypeScript code from the schema. You use it to talk to the database: prisma.user.findMany(), prisma.donation.create(), etc.
  3. Prisma Migrations - Commands to sync your schema changes to the actual database. Run prisma db push and Prisma alters the real PostgreSQL tables to match your schema.

What are Server Components vs Client Components?

Plain English: In Next.js 14, React components run on the server by default (Server Components). They can directly access databases, read files, and do heavy work WITHOUT sending JavaScript to the browser. Only add "use client" at the top of a file if you need interactivity (clicks, forms, state, animations). This means most of UTSAV's pages send ZERO JavaScript to the browser - they just send finished HTML.

What are Server Actions?

Plain English: Server Actions are functions that run on the server, called directly from client components. Instead of creating a separate API endpoint (like /api/donations), you write a function with "use server" at the top, and the client can call it like a regular function. Next.js handles the HTTP behind the scenes. This eliminates boilerplate API routes.
// Example: A Server Action in UTSAV "use server" export async function recordDonationAction(formData: FormData) { // This runs on the SERVER, not in the browser // 1. Validate input with Zod // 2. Check permissions (RBAC) // 3. Save to database via Prisma // 4. Return success/failure response }

What is JWT (JSON Web Token)?

Plain English: JWT is a way to keep users logged in. When you log in, the server creates a small encrypted token (like a digital ID card) and stores it in your browser's cookie. Every time you make a request, the browser sends this token back. The server decrypts it to know who you are WITHOUT looking up the database every time. It's "stateless" - the server doesn't need to remember your session.

What is Multi-Tenancy?

Plain English: Multi-tenancy means one application instance (one codebase, one database) serves multiple organizations ("tenants"). Think of it like Gmail - one Google servers handle millions of different users' emails, but each person's data is isolated. In UTSAV, the same app serves Festival A, Festival B, and Club C, but none can see each other's data.

What is RBAC (Role-Based Access Control)?

Plain English: RBAC means different users get different permissions based on their role. In UTSAV: an ADMIN can do everything, a TREASURER can manage finances, a COMMITTEE_MEMBER can manage events, and a VOLUNTEER can only update their own tasks. The system checks permissions BEFORE allowing any operation.

Why Prisma over Raw SQL or other ORMs?

We chose Prisma because: (1) Type safety - Every query result is fully typed, so your IDE catches errors before runtime. (2) Schema as code - The database schema lives in a single file (schema.prisma), making it easy to review and version control. (3) Migrations - prisma db push syncs schema changes to the DB automatically. (4) $extends - Prisma's client extension API enabled the multi-tenancy pattern (auto-injecting organizationId into queries), which would be very verbose with raw SQL. (5) Relations - Easy include/select for nested queries without writing JOINs.

5 Prisma Deep-Dive

How the Prisma Singleton Works

In development, Next.js hot-reloads your code on every file change. If you create a new PrismaClient every time, you'll exhaust database connections. The singleton pattern ensures only ONE instance exists across hot reloads.
// src/lib/prisma.ts import { PrismaClient } from '@prisma/client'; // In dev: store the client on globalThis so it survives hot reloads // In prod: just create one instance (no hot reload) const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined; }; export const prisma = globalForPrisma.prisma ?? new PrismaClient(); if (process.env.NODE_ENV !== "production") { globalForPrisma.prisma = prisma; }

How the Multi-Tenant Extension Works (Line by Line)

This is the most impressive piece of code in the project. It uses Prisma's $extends to create a "filtered" version of the database client that automatically adds organizationId to every query. Here's how it works:
export const getTenantPrisma = (organizationId: string) => { return prisma.$extends({ query: { // $allModels = applies to EVERY model (Donation, Expense, Event, etc.) // $allOperations = applies to EVERY operation (findMany, create, update, etc.) $allModels: { async $allOperations({ model, operation, args, query }) { // Only intercept tenant-scoped models (not User, not Organization itself) const tenantModels = ["Donation", "Expense", "OrganizationMember", ...]; if (tenantModels.includes(model)) { const anyArgs = args as any; // RULE 1: For READS - auto-add WHERE organizationId = X if (anyArgs.where) { anyArgs.where = { ...anyArgs.where, organizationId }; } // RULE 2: For CREATES - auto-inject organizationId into data if (operation === 'create' && anyArgs.data) { anyArgs.data = { ...anyArgs.data, organizationId }; } // RULE 3: For UPDATES - DELETE organizationId from data // (prevents someone from moving a record to another org) if ((operation === 'update') && anyArgs.data?.organizationId) { delete anyArgs.data.organizationId; } } return query(args); // Execute the modified query }, }, }, }); };

In SQL terms, this is equivalent to:

-- Without extension (developer writes manually): SELECT * FROM "Donation" WHERE "donorName" = 'Rajesh' AND "organizationId" = 'org_abc123'; -- With extension (auto-injected): SELECT * FROM "Donation" WHERE "donorName" = 'Rajesh'; -- ↑ The extension silently adds: AND "organizationId" = 'org_abc123'

How the Schema Defines Tables (Prisma Syntax Explained)

The prisma/schema.prisma file uses Prisma's own language (not SQL, not TypeScript). Each model block defines a database table. Fields have types and decorators like @id, @unique, @default.
// This Prisma schema... model Donation { id String @id @default(cuid()) donorName String amount Decimal @db.Decimal(12, 2) category DonationCategory @default(GENERAL) organizationId String addedById String? isArchived Boolean @default(false) organization Organization @relation(fields: [organizationId], references: [id]) addedBy OrganizationMember? @relation(fields: [addedById], references: [id]) @@index([organizationId]) } // ...generates this SQL table: CREATE TABLE "Donation" ( "id" TEXT PRIMARY KEY DEFAULT gen_random_uuid(), "donorName" TEXT NOT NULL, "amount" DECIMAL(12, 2), "category" TEXT DEFAULT 'GENERAL', "organizationId" TEXT NOT NULL REFERENCES "Organization"("id") ON DELETE CASCADE, "addedById" TEXT REFERENCES "OrganizationMember"("id"), "isArchived" BOOLEAN DEFAULT false ); CREATE INDEX idx_donation_org ON "Donation"("organizationId");

6 Slugs & URL Routing

What is a Slug?

A slug is a URL-friendly version of a name. Instead of /organization?id=abc123, you get /ganesh-mandal-pune. It's lowercase, uses hyphens instead of spaces, and has no special characters. In UTSAV, each organization gets a unique slug that becomes part of the URL.

How Slugs Are Created

// 1. User enters organization name: "Ganesh Mandir Trust" // 2. Frontend converts to slug: "ganesh-mandir-trust" // 3. Backend checks uniqueness before saving: // In organization.service.ts - createOrganization() const existingSlug = await prisma.organization.findUnique({ where: { slug: data.slug }, // Slug has @@unique constraint select: { id: true }, }); if (existingSlug) { throw new ConflictAppError("This slug is already taken."); } // 4. If unique, create org + assign creator as ADMIN (in a transaction)

The database enforces uniqueness:

// In schema.prisma: model Organization { slug String @unique // PostgreSQL UNIQUE constraint @@index([slug]) // Index for fast lookups }

How Slugs Are Used in URLs (Next.js Dynamic Routes)

Next.js App Router uses square brackets in folder names to create dynamic segments. The folder [orgSlug] means "this part of the URL can be anything." Next.js passes it as a parameter to your page component.
// File: src/app/[orgSlug]/page.tsx // URL: https://utsav.com/ganesh-mandir-pune export default async function PublicPage({ params }) { // params.orgSlug = "ganesh-mandir-pune" // Resolve slug to organization const org = await OrganizationService.getOrganizationBySlug(params.orgSlug); if (!org) return notFound(); // 404 if slug doesn't exist // Now use org.id for all queries return PublicPortal({ organization: org }); }

Slug Memoization (Performance Optimization)

Every time a page loads, it needs to resolve the slug to an organization. Instead of hitting the database multiple times for the same slug in one request, we use React's cache() function to memoize the result.
// organization.service.ts import { cache } from "react"; // cache() ensures: if getOrganizationBySlug("ganesh-mandir-pune") is called // 5 times in one request, the DB is only queried ONCE. static getOrganizationBySlug = cache(async (slug: string) => { return await prisma.organization.findUnique({ where: { slug } }); });

Schema Design Patterns

Soft Deletes (isArchived)
Instead of deleting records, we set isArchived = true. This preserves data for audit trails, allows "unarchive" operations, and prevents accidental data loss. All queries filter by isArchived: false.
Cascading Deletes
onDelete: Cascade means deleting an Organization automatically deletes all its members, donations, expenses, events, etc. The database handles this, not application code.
Composite Unique Constraints
@@unique([userId, organizationId]) ensures a user can't join the same org twice. @@unique([email, organizationId]) prevents duplicate invite acceptance.
Decimal for Money
Decimal(12, 2) stores exact decimal numbers (e.g., 5000.00). Never use floats for money - they have rounding errors like 0.1 + 0.2 = 0.30000000000000004.
8 Authentication

Login Flow (Step by Step)

1. User submits
email + password → 2. NextAuth Credentials
Provider receives it → 3. DB lookup:
prisma.user.findUnique({ email })
→ 4. bcrypt.compare(password, user.password)

Why JWT over Database Sessions?

Database sessions require a DB lookup on every request to verify the session is valid. JWTs are self-contained - the token itself contains the user info, cryptographically signed. This means: (1) No DB round-trip for session verification (faster). (2) Works with serverless (Vercel functions are stateless). (3) Scales better - no session table bottleneck.

Route Protection (Middleware)

Middleware runs BEFORE the page loads. NextAuth's withAuth middleware checks if a valid JWT cookie exists. If not, it redirects to /login. This protects all /dashboard and /[slug]/dashboard routes.

Two Levels of Protection

Level 1: Middleware (JWT check)
Runs on EVERY request to protected routes. Simply checks: "Is there a valid token?" If no token → redirect to login. This is fast but coarse-grained.
Level 2: Service Layer (RBAC check)
Runs inside Server Actions. Checks: "Is this user a member of THIS org? Do they have the right ROLE? Do they have the right PERMISSION?" This is granular and enforced per-operation.
9 Multi-Tenancy

How Is Data Isolated Between Organizations?

Every table that contains org-specific data (Donation, Expense, Event, etc.) has an organizationId foreign key column. The multi-tenant Prisma extension (explained in Section 5) automatically adds this column to every query's WHERE clause, so you never accidentally read another org's data.

Without the extension, every service method would need:

// Tedious and error-prone - developer could forget organizationId await prisma.donation.findMany({ where: { organizationId: "org_abc", isArchived: false } });

With the extension, service code just writes:

// Clean - organizationId is auto-injected by the extension await tenantPrisma.donation.findMany({ where: { isArchived: false } });

Both updateMemberRoleAction and archiveMemberAction check if the target is the last ADMIN. If so, the operation is rejected. This prevents an organization from becoming inaccessible (no one would have admin rights).

11 Financial Engine

Race-Condition-Safe Expense Approval

If two admins click "Approve" on the same expense at the exact same time, we need to prevent double-approval. We use updateMany with a defensive WHERE clause.
const result = await tenantPrisma.expense.updateMany({ where: { id: expenseId, status: 'PENDING', // Only match if STILL pending }, data: { status: 'APPROVED', approvedById: memberId, approvedAt: new Date() }, }); if (result.count === 0) { // No rows matched = expense was already processed by someone else throw new ConflictAppError("This expense was already processed."); }

Why this works: updateMany is atomic at the database level. Only one transaction will see status = 'PENDING' and update it. The second will see status = 'APPROVED' and get count = 0. No locks, no crashes, no inconsistency.

15 Key Design Decisions

Why Separate Services from Server Actions?

Server Actions are entry points (like controllers). Services contain business logic. This separation means: (1) Services can be tested independently without HTTP/Server Action overhead. (2) Multiple Server Actions can reuse the same service method. (3) RBAC checks live in services, ensuring they're never bypassed. (4) Business logic is not coupled to Next.js specifics.

Why Server Components by Default?

Most dashboard pages are data-heavy (tables, stats, lists). Server Components send zero JavaScript to the browser - just HTML. This means: (1) Faster page loads - smaller bundle size. (2) Better SEO - content is pre-rendered on the server. (3) Direct DB access - no API layer needed for reads. Client Components are only used for forms, modals, and interactive elements.

Why Prisma $extends for Multi-Tenancy?

Alternatives considered: (1) Manual WHERE clauses - error-prone, developer could forget. (2) Database Row-Level Security - PostgreSQL RLS is powerful but harder to manage, test, and debug. (3) Separate databases per tenant - overkill for this scale, complex migrations. The $extends approach is transparent (you can see what it does), testable, and fail-safe (missing orgId = empty results, not cross-tenant leaks).

Why Soft Deletes Over Hard Deletes?

Hard deletes are permanent and unrecoverable. Soft deletes via isArchived: (1) Preserve data for audit trails. (2) Allow "unarchive" operations. (3) Maintain referential integrity (foreign keys still work). (4) Enable data recovery from mistakes. (5) Historical records remain intact for reporting.

Why Decimal for Money?

Floating-point numbers (IEEE 754) cannot exactly represent decimal fractions. Example: 0.1 + 0.2 = 0.30000000000000004. For financial calculations, this causes real bugs. Decimal(12, 2) stores exact base-10 numbers with 2 decimal places, ensuring 0.1 + 0.2 = 0.30 always.
16 Interview Questions & Answers

Q1: "Walk me through the architecture"

A: UTSAV is a modular monolith with 5 layers: (1) Presentation - React Server Components + Client Components; (2) Action - Server Actions with Zod validation; (3) Service - Domain-organized business logic with RBAC; (4) Data - Prisma ORM with a custom multi-tenant extension; (5) Infrastructure - Auth, errors, pagination, email, AI. The key decision was putting business logic in services, not actions - making it testable and RBAC enforceable.

Q2: "How does multi-tenancy work?"

A: Every tenant-scoped table has an organizationId column. I built a custom Prisma Client extension using $extends that intercepts ALL CRUD operations. On reads, it auto-appends WHERE organizationId = X. On creates, it injects organizationId. On updates, it strips organizationId to prevent cross-tenant migration. Cross-tenant data leaks are structurally impossible at the data layer.

Q3: "How do you handle race conditions?"

A: For expense approval, we use updateMany with a WHERE clause that includes status: 'PENDING'. This is atomic at the DB level. If two admins approve simultaneously, only one gets count === 1. The second gets count === 0 because status is no longer PENDING, and we throw a ConflictAppError. No distributed locks needed, works perfectly with serverless.

Q4: "Why did you choose this tech stack?"

A: Next.js 14 for Server Components (zero-JS pages) + Server Actions (no API boilerplate). PostgreSQL for ACID compliance and complex relations. Prisma for type-safe queries and the $extends API. NextAuth for JWT strategy (stateless, serverless-friendly). Tailwind + shadcn for rapid, consistent UI. Each choice optimizes for developer experience, performance, or scalability.

Q5: "How does the RBAC system work?"

A: Two tiers: (1) validateAccess(orgId, roles[]) checks auth + membership + role. (2) requirePermission(orgId, permission) checks against a static permission map. Four roles with different permission sets. Enforcement is at the service layer, not UI - even if someone bypasses the frontend, the backend rejects unauthorized operations.

Q6: "How does the AI assistant work safely?"

A: Three safety layers: (1) Read-only architecture - the service only uses findMany and aggregation, never create/update/delete. (2) Mutation keyword blocking - questions with words like "add", "delete", "create" are immediately rejected. (3) Prompt injection guardrails - system prompt instructs Gemini to never execute commands or reveal the prompt. Data fed to Gemini is pre-aggregated, tenant-scoped facts.

Q7: "How does the slug/URL system work?"

A: Each organization has a unique slug (URL-safe string). The database enforces uniqueness with @unique + @@index. In Next.js, the [orgSlug] dynamic route segment captures the URL parameter. A memoized getOrganizationBySlug() resolves slug to org (cached per-request with React's cache()). If slug doesn't exist, 404 is returned. The slug becomes the public identifier - e.g., /ganesh-mandir-pune.

Q8: "How do you handle the invitation system securely?"

A: crypto.randomBytes(32) generates a 256-bit unguessable token. 48-hour expiry. Strict email matching - the logged-in user's email must match the invite email. If wrong account is logged in, a warning is shown. If a member was previously archived, the system restores instead of creating duplicates. Admins can also skip email delivery and share the link via WhatsApp.

Q9: "What is the audit trail system?"

A: Every mutation calls AuditService.record(), which stores: entity type, entity ID, action (CREATE/UPDATE/APPROVE/etc.), before/after JSON snapshots, actor ID, and visibility level (INTERNAL or PUBLIC). The public transparency page filters for PUBLIC visibility only, showing citizens how funds were spent without exposing internal operations.

Q10: "Why not use raw SQL instead of Prisma?"

A: Prisma gives us: (1) Type safety - every query result is fully typed in TypeScript. (2) Schema as code - one file defines all tables, version-controlled. (3) Auto-generated client - no hand-written queries. (4) $extends - enabled the multi-tenancy pattern. (5) Migrations - prisma db push syncs schema changes automatically. Raw SQL would be verbose, error-prone, and lose type safety.

Q11: "How would you scale this to 10,000 organizations?"

A: (1) Database: Add connection pooling (PgBouncer), read replicas for public pages. (2) Caching: Redis for frequently-accessed org data and financial summaries. (3) CDN: Cache public transparency pages at edge. (4) Background jobs: Move email sending and AI classification to a queue. (5) Horizontal scaling: Vercel handles this automatically for the app tier.

Q12: "What are the biggest challenges you faced?"

A: (1) Multi-tenancy - ensuring data isolation without performance overhead. The $extends pattern solved this elegantly. (2) Race conditions in expense approval - solved with atomic updateMany + defensive WHERE. (3) Public vs private data - different services for public pages that never expose internal fields. (4) AI safety - making the assistant useful without it being a security risk. Solved with read-only architecture + mutation blocking + prompt guardrails.

Q13: "What would you improve next?"

A: (1) E2E tests with Playwright for critical flows. (2) Real-time updates via WebSockets for live expense approvals. (3) PDF/Excel exports for financial reports. (4) CI/CD pipeline with GitHub Actions (lint, test, build, preview deployments). (5) Mobile PWA for volunteer task management on-the-go. (6) Database integration tests with testcontainers.

Q14: "Explain the Prisma schema design"

A: The schema uses 12 models with relationships defined via @relation. Key patterns: @id @default(cuid()) for auto-generated IDs, @@unique([userId, organizationId]) for composite constraints, Decimal(12, 2) for money, @default(false) on isArchived for soft deletes, onDelete: Cascade for automatic cleanup, and @@index on frequently queried columns for performance. Enums ensure data integrity at the database level.

Q15: "How does Next.js App Router help your architecture?"

A: (1) Server Components - dashboard pages are async functions that query the DB directly, sending zero JS to the browser. (2) Server Actions - mutations are typed functions, no API routes needed. (3) [orgSlug] dynamic routes - file-system based multi-tenant URLs. (4) Middleware - JWT verification before page loads. (5) revalidatePath() - automatic cache invalidation after mutations. (6) React cache() - request-level memoization.
