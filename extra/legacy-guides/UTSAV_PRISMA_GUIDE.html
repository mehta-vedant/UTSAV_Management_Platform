1 How Prisma Actually Works

The Big Picture: What You Write vs What Happens Automatically

YES - You ONLY write the schema.prisma file. Everything else is automatic:
WhatWho Does ItHow
Database tablesYou (one command)Run npx prisma db push - Prisma reads your schema and creates/modifies actual PostgreSQL tables
TypeScript typesAutomaticPrisma generates node_modules/.prisma/client with full types for every model, field, and relation
Database clientAutomaticPrismaClient is auto-generated with methods like findMany(), create(), update() etc.
MigrationsYou (one command)Run npx prisma migrate dev when you change the schema - generates SQL migration files
Relations/JOINsAutomaticYou define relations in schema with @relation, Prisma handles SQL JOINs behind the scenes
ValidationAutomaticString = required, String? = optional, @unique = no duplicates - enforced at DB level

The Workflow (Step by Step)

// STEP 1: You write the schema (prisma/schema.prisma) model User { id String @id @default(cuid()) email String @unique name String } // STEP 2: Run command to sync schema to database npx prisma db push // STEP 3: Prisma automatically generates the TypeScript client // You get a fully-typed 'prisma' object you can use in your code: import { prisma } from "@/lib/prisma"; // Now you can do CRUD operations with full TypeScript autocomplete: await prisma.user.findMany(); // SELECT * FROM "User" await prisma.user.create({ data: {...} }); // INSERT INTO "User" await prisma.user.update({ ... }); // UPDATE "User" SET ... await prisma.user.delete({ ... }); // DELETE FROM "User" WHERE ... // That's it. No SQL. No API endpoints. Just typed function calls.

The PrismaClient Singleton (What's in prisma.ts?)

// src/lib/prisma.ts - This file is only 11 lines import { PrismaClient } from "@prisma/client"; // 'globalThis' is a special object that persists across hot reloads in dev const globalForPrisma = global as unknown as { prisma: PrismaClient }; // Either reuse existing client (from globalThis) or create new one export const prisma = globalForPrisma.prisma || new PrismaClient({ log: ["query"] }); // In dev, save to globalThis so hot reload reuses it (prevents connection leak) if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
Why the singleton? In development, Next.js hot-reloads your code on every file save. Without this pattern, every reload would create a NEW PrismaClient, opening a new database connection. After 10-15 saves, you'd hit PostgreSQL's connection limit and crash. The singleton stores ONE client on globalThis and reuses it.

Table-Level Decorators (Starts with @@)

DecoratorMeaningSQL EquivalentExample
@@index([field]) Create a database index on this column for faster queries CREATE INDEX idx_name ON "Table"("field") @@index([organizationId])
@@unique([a, b]) Composite unique: the COMBINATION of these fields must be unique (each individually can repeat) UNIQUE("a", "b") @@unique([userId, organizationId])
@@index([a, b]) Composite index on multiple columns (for queries filtering by both) CREATE INDEX ON "Table"("a", "b") @@index([organizationId, offeringDate])
@@unique vs @unique: @unique on a field means THAT field alone must be unique. @@unique([userId, organizationId]) means the PAIR must be unique - the same userId can appear multiple times IF the organizationId is different. This prevents a user from joining the same org twice.

The ? Symbol (Optional Fields)

// Required fields (NOT NULL in SQL): email String // MUST have a value amount Decimal // MUST have a value status ExpenseStatus // MUST have a value // Optional fields (? = nullable in SQL): phone String? // CAN be null notes String? // CAN be null eventId String? // CAN be null (donation not tied to any event)
In TypeScript after generation: String becomes string, String? becomes string | null. The Prisma client forces you to handle nullable values.

5 Relations (How Tables Connect)

One-to-Many Relation (Most Common)

// One Organization has MANY members // One OrganizationMember belongs to ONE Organization model Organization { id String @id @default(cuid()) name String members OrganizationMember[] // This is the "many" side (array) } model OrganizationMember { id String @id @default(cuid()) organizationId String // Foreign key field (stores the org's ID) organization Organization // The relation field (NOT a column - used by Prisma) @relation(fields: [organizationId], references: [id], onDelete: Cascade) }
Anatomy of @relation:
fields: [organizationId] = "This model's field that stores the foreign key"
references: [id] = "The field in the other model this points to"
onDelete: Cascade = "If the Organization is deleted, delete all its members too"
In SQL: "organizationId" TEXT REFERENCES "Organization"("id") ON DELETE CASCADE

Named Relations (When Multiple Relations to Same Model)

// Expense has TWO relations to OrganizationMember: // 1. Who ADDED the expense (addedById) // 2. Who APPROVED the expense (approvedById) model Expense { id String @id @default(cuid()) addedById String approvedById String? addedBy OrganizationMember @relation("ExpenseAddedBy", fields: [addedById], references: [id]) approvedBy OrganizationMember?@relation("ExpenseApprovedBy", fields: [approvedById], references: [id]) } model OrganizationMember { id String @id @default(cuid()) expensesAdded Expense[] @relation("ExpenseAddedBy") // Must match the name! expensesApproved Expense[] @relation("ExpenseApprovedBy") // Must match the name! }
Why named relations? When two fields in the same model point to the same other model, Prisma can't automatically figure out which is which. The name acts as a label to disambiguate.

Optional Relations (?)

// A Donation MIGHT be tied to an Event, or might not model Donation { eventId String? // Optional foreign key (can be null) event Event? // Optional relation (marked with ?) @relation(fields: [eventId], references: [id]) } // A Donation MUST belong to an Organization model Donation { organizationId String // Required foreign key (no ?) organization Organization // Required relation (no ?) @relation(fields: [organizationId], references: [id], onDelete: Cascade) }

Many-to-Many Relation (Junction Table)

// An Event can have MANY Members assigned // A Member can be assigned to MANY Events // This creates a "junction table" called EventAssignment model Event { id String @id @default(cuid()) assignments EventAssignment[] // The junction table records } model OrganizationMember { id String @id @default(cuid()) eventAssignments EventAssignment[] // The junction table records } // The junction table (explicitly defined for extra fields) model EventAssignment { id String @id @default(cuid()) eventId String // FK to Event organizationMemberId String // FK to OrganizationMember createdAt DateTime @default(now()) // Extra field! event Event @relation(fields: [eventId], references: [id], onDelete: Cascade) member OrganizationMember @relation(fields: [organizationMemberId], references: [id], onDelete: Cascade) @@unique([eventId, organizationMemberId]) // Can't assign same member twice to same event }

6 Enums (Restricted Value Sets)

What Are Enums?

Enums restrict a field to a fixed set of values. Instead of status String (where someone could type "APPROVEDD" by accident), you use status ExpenseStatus where only PENDING, APPROVED, or REJECTED are valid. This catches bugs at the database level.

9 Complete CRUD Operations

CREATE - Adding Records

import { prisma } from "@/lib/prisma"; // 1. CREATE ONE record (basic) const user = await prisma.user.create({ data: { email: "vedant@example.com", name: "Vedant", password: "$2a$12$...", // bcrypt hashed }, }); // Returns the created user with auto-generated id, createdAt, etc. // 2. CREATE with related record (nested create) const org = await prisma.organization.create({ data: { name: "Ganesh Mandir Trust", slug: "ganesh-mandir-trust", type: "FESTIVAL", // Simultaneously create the first member (admin) members: { create: [{ email: "vedant@example.com", role: "ADMIN", userId: user.id, }], }, }, include: { members: true }, // Include the created members in response }); // 3. CREATE MANY records at once const result = await prisma.donation.createMany({ data: [ { donorName: "Rajesh", amount: 5000, organizationId: org.id }, { donorName: "Suresh", amount: 10000, organizationId: org.id }, { donorName: "Mahesh", amount: 2500, organizationId: org.id }, ], }); // result.count = 3 (number of records created) // 4. CREATE with default values (omitting fields uses @default) const expense = await prisma.expense.create({ data: { title: "Flower decoration", amount: 3000, addedById: memberId, organizationId: orgId, // category defaults to MISCELLANEOUS // status defaults to PENDING // isArchived defaults to false // requestedAt defaults to now() }, });

READ - Querying Records

// 1. FIND UNIQUE (by unique field) const user = await prisma.user.findUnique({ where: { email: "vedant@example.com" }, }); // Returns: { id: "clx...", email: "vedant@example.com", name: "Vedant", ... } or null // 2. FIND FIRST (first match) const org = await prisma.organization.findFirst({ where: { slug: "ganesh-mandir-trust" }, }); // 3. FIND MANY (list with filters) const donations = await prisma.donation.findMany({ where: { organizationId: "org_abc123", isArchived: false, // Optional additional filters: category: "GENERAL", // Exact match amount: { gte: 1000 }, // Greater than or equal donorName: { contains: "Raj" }, // Partial match (LIKE %Raj%) }, include: { addedBy: true, // JOIN with OrganizationMember event: true, // JOIN with Event }, select: { id: true, donorName: true, amount: true, // If you use 'select', ONLY listed fields are returned // If you use 'include', ALL original fields + relations are returned }, orderBy: { createdAt: "desc" }, // Newest first skip: 0, // Offset (for pagination) take: 10, // Limit (page size) }); // 4. COUNT records const total = await prisma.donation.count({ where: { organizationId, isArchived: false }, }); // Returns: 42 // 5. AGGREGATE (sum, avg, min, max) const stats = await prisma.donation.aggregate({ where: { organizationId }, _sum: { amount: true }, // SUM of all amounts _avg: { amount: true }, // Average amount _count: { amount: true }, // Count }); // Returns: { _sum: { amount: 50000 }, _avg: { amount: 5000 }, _count: { amount: 10 } } // 6. GROUP BY const byCategory = await prisma.expense.groupBy({ by: ["category"], where: { organizationId, status: "APPROVED" }, _sum: { amount: true }, _count: { id: true }, orderBy: { _sum: { amount: "desc" } }, }); // Returns: [ // { category: "DECORATION", _sum: { amount: 25000 }, _count: { id: 5 } }, // { category: "FOOD", _sum: { amount: 15000 }, _count: { id: 8 } }, // ... // ]

UPDATE - Modifying Records

// 1. UPDATE ONE record by unique identifier const updated = await prisma.expense.update({ where: { id: expenseId }, data: { status: "APPROVED", approvedById: memberId, approvedAt: new Date(), }, }); // 2. UPDATE MANY records (bulk update) const result = await prisma.expense.updateMany({ where: { organizationId, status: "PENDING", // Note: updateMany can only do simple where clauses (no nested relations) }, data: { status: "APPROVED", approvedById: memberId, }, }); // result.count = number of rows updated // 3. UPSERT (create or update) const member = await prisma.organizationMember.upsert({ where: { // Composite unique for the lookup userId_organizationId: { userId: user.id, organizationId: org.id }, }, update: { role: "ADMIN", // If exists, update role }, create: { userId: user.id, email: user.email, organizationId: org.id, role: "ADMIN", // If not exists, create with this data }, });

DELETE - Removing Records

// 1. DELETE ONE record await prisma.eventAssignment.delete({ where: { // Use composite unique for junction tables eventId_organizationMemberId: { eventId: eventId, organizationMemberId: memberId, }, }, }); // 2. DELETE MANY records (bulk delete) const result = await prisma.eventRegistration.deleteMany({ where: { eventId }, }); // result.count = number deleted // NOTE: In UTSAV we almost never delete - we use soft deletes (isArchived = true) await prisma.donation.update({ where: { id: donationId }, data: { isArchived: true, archivedAt: new Date(), archivedById: memberId }, });

11 Transactions (All-or-Nothing)

What Are Transactions?

A transaction groups multiple database operations together. Either ALL succeed or ALL fail. If any operation throws an error, all previous operations in the transaction are rolled back. This prevents partial updates that leave your data in an inconsistent state.

Transaction Examples from UTSAV

// Example 1: Create org + assign admin (both must succeed) await prisma.$transaction(async (tx) => { // 'tx' is a transactional Prisma client const org = await tx.organization.create({ data: { name: "New Festival", slug: "new-festival" }, }); // If this fails, the organization create above is ROLLED BACK await tx.organizationMember.create({ data: { userId: user.id, email: user.email, organizationId: org.id, role: "ADMIN", }, }); return org; }); // Example 2: Delete org (clean up all related data) await prisma.$transaction(async (tx) => { await tx.organizationMember.deleteMany({ where: { organizationId } }); await tx.organizationInvitation.deleteMany({ where: { organizationId } }); return await tx.organization.delete({ where: { id: organizationId } }); }); // Example 3: Interactive transaction (read then write) await prisma.$transaction(async (tx) => { const expense = await tx.expense.findUnique({ where: { id: expenseId } }); if (expense.status !== "PENDING") { throw new Error("Already processed"); } return await tx.expense.update({ where: { id: expenseId }, data: { status: "APPROVED" }, }); });

CommandWhat It DoesWhen to Use
npx prisma generateGenerates the TypeScript client from schemaAfter changing schema.prisma (also runs on npm install via postinstall)

npx prisma validateChecks schema for errors without applyingValidating schema before push/migrate
npx prisma introspectReads existing DB and generates schema from itAdopting Prisma for existing database
db push vs migrate dev: db push is faster and simpler - it syncs your schema directly. migrate dev creates a versioned SQL migration file in prisma/migrations/ which is better for team collaboration and production. UTSAV uses db push during development.
